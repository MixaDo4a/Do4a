# Do4a Staff Only: контекст проекта

Этот файл предназначен для следующего разработчика или ИИ. Он описывает текущую реализацию по состоянию репозитория, а не только первоначальную идею проекта.

## Назначение и концепция

Do4a Staff Only — закрытое внутреннее web/PWA-приложение для операционного управления магазинами спортивного питания. Оно объединяет рабочие процессы сотрудников магазинов и управляющих:

- планирование и просмотр графика;
- открытие и закрытие смен с кассовым отчётом;
- постановку, выполнение и архивирование задач;
- утренний и вечерний распорядок дня;
- чек-листы и их архив;
- акции поставщиков и закупочные заказы;
- зарплату, премии, штрафы и другие корректировки;
- остаток наличных в кассах и РКО/ПКО;
- уведомления внутри приложения и browser push;
- управление сотрудниками, магазинами и ролями.

Интерфейс сделан как мобильное приложение с нижней навигацией и адаптацией под desktop. Основная визуальная концепция: тёмный фон с тематическими изображениями, красные акценты Do4a, полупрозрачные информационные панели, компактные рабочие формы и просмотр широких таблиц графика с горизонтальной прокруткой.

## Стек

- Next.js 15 App Router.
- React 19, TypeScript 5.7.
- Tailwind CSS 3.4 и локальные CSS-классы в `src/app/globals.css`.
- `lucide-react` для иконок.
- Zustand присутствует в зависимостях; основной серверный поток данных реализован через Server Components и route handlers.
- Supabase JS 2.x и `@supabase/ssr` для Auth, PostgreSQL, RLS, Storage и RPC.
- PostgreSQL 17 в локальной конфигурации Supabase.
- `web-push` для серверной отправки push-уведомлений.
- Vercel используется как production-хостинг Next.js.
- OpenAI Vision API используется для проверки фотографий распорядка дня, если на сервере задан `OPENAI_API_KEY`.

## Реализованные функции

### Аутентификация и доступ

Вход выполняется через Supabase Auth по email/паролю или email-ссылке. Профиль приложения связан с Auth-пользователем через `profiles.id`. Доступ к данным ограничен ролью, назначениями сотрудника и доступными магазинами. Для серверных операций используются SSR-клиент Supabase и отдельный service-role клиент; service-role ключ не должен попадать в браузер.

### Магазины и сотрудники

Есть CRUD/архивирование магазинов, создание/редактирование/мягкое удаление/восстановление сотрудников, назначение сотрудников магазинам и назначение ролей через защищённые RPC. Удалённые сотрудники не должны попадать в новые рабочие выборки, но исторические записи сохраняются.

### График и смены

Управляющий редактирует график по магазинам и сотрудникам, в том числе массово. Поддерживаются статусы P1/P2, выходной, отпуск, больничный и пустой день, включая вторичного сотрудника. Менеджер видит собственный график. На главной управляющего график должен отображаться отдельной мини-таблицей для каждого подчинённого магазина с ближайшими днями и сотрудниками.

Открытие смены привязано к сегодняшней дате. Закрытие выполняется серверной функцией `close_shift`, фиксирует отчёт, покупюрник, файлы и snapshot. Текущие смены отделены от архива закрытых смен. Автозакрытие и напоминания предусмотрены RPC/route-инфраструктурой.

### Касса

Покупюрник хранит количества номиналов и рассчитывает сумму сервером. Сумма наличных магазина выводится на главной и в `/cash`; движения РКО/ПКО хранятся в `store_cash_movements`. Для закрытия смены ранее исключены номиналы 0.1 и 0.5. Файлы отчёта смены хранятся в Supabase Storage.

### Задачи

Задачу можно назначить сотруднику и нескольким магазинам, указать срок или оставить бессрочной. Есть статусы открыта/в работе/выполнена/просрочена/отменена, комментарии, файлы, фильтры и архив завершённых задач пользователя. Повторения поддерживаются через `task_recurrence_rules` и route `/api/tasks/recurrences`.

В уведомлении о задаче должны указываться сотрудник и магазин. Автор задачи не должен получать обычное уведомление о постановке собственной задачи. Для защиты от быстрых повторных нажатий используются серверная дедупликация/уникальные ограничения и блокировка состояния формы.

### Распорядок дня

Есть утренний и вечерний распорядок, шаблоны и редактирование управляющим. Пункты имеют иерархию, порядок, отметку выполнения и время отметки. Менеджер отмечает пункты после открытия смены; управляющий видит текущий прогресс по магазинам и может корректировать отметку вручную.

Для пункта можно включить обязательную фотографию и загрузить эталонное фото. Фотография сотрудника сохраняется отдельно, а серверный модуль `routine-photo-ai.ts` может сравнивать её с эталоном через OpenAI и сохранить результат/комментарий. При отсутствии ключа или невозможности проверки применяется ручная проверка.

### Чек-листы

Создаются проверки по магазину и сотруднику, пункты имеют оценку, комментарий и фото. Доступны проведение и архив. Менеджеры получили доступ к своим магазинам, управляющие — к подчинённым магазинам, проверяющий — к своей области.

### Акции и закупки

Роль закупщика и связанные права добавлены миграциями. Закупщик создаёт заказ поставщику, выбирает магазин, добавляет счёт, после чего кладовщик получает уведомление и меняет статус заказа. Есть акции поставщика с выбором нескольких магазинов. Для менеджера нижняя вкладка называется «Акции», в остальных интерфейсах используется «Закуп/Акции».

### Зарплата

Есть расчёт периода, зарплатные записи, премии, штрафы, авансы, списания и snapshots. Расчёт использует серверные функции. Удалённые сотрудники не должны отображаться в текущих списках зарплаты.

### Уведомления и push

Внутренние уведомления хранятся в `notifications`, доставки и дедупликация — в `notification_deliveries`. Push-подписки хранятся в `push_subscriptions`, сервер отправляет их через `web-push`, а `public/sw.js` обрабатывает push. Есть `/api/push/config`, `/api/push/status`, `/api/push/subscribe`, `/api/push/sync`.

Подписка создаётся после пользовательского нажатия «Включить push». На клиенте используется App Badge API для количества непрочитанных уведомлений, если браузер его поддерживает. Отправка push зависит от VAPID-параметров, активной подписки конкретного сотрудника и корректной серверной доставки; наличие строки в `notifications` само по себе не означает успешную доставку push.

## Роли и права

Фактически используемые коды ролей определяются в `src/lib/auth/role-constants.ts` и миграциях. В проекте встречаются:

- `manager` — сотрудник магазина/менеджер: собственные смены, задачи, график, распорядок, доступные чек-листы и акции в режиме просмотра;
- `auditor` — проверяющий: проверки, архивы и магазины своей области;
- `store_manager` — управляющий: подчинённые магазины, сотрудники, график, смены, задачи, распорядок, чек-листы, кассы, зарплата и административные операции по области;
- `warehouse_manager` — кладовщик: складские процессы и заказы в разрешённых магазинах;
- `warehouse_assistant` — помощник кладовщика: ограниченный складской процесс и задачи;
- `buyer` — закупщик: поставщики, акции и заказы;
- `super_admin` — полный административный доступ, включая сотрудников, магазины и финансовые операции;
- `developer` — технический расширенный доступ, используемый для сопровождения и специальных операций.

Роли могут комбинироваться. UI-фильтрация не заменяет RLS: окончательное право должно проверяться сервером/RPC и политиками Supabase.

## Важные настройки Supabase и Vercel

- В `supabase/config.toml` включены API, Auth, Storage и Realtime; API изначально рассчитан на схему `public` и `graphql_public`.
- В публичный клиент допустимы только `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и публичный VAPID key.
- На сервере нужны `SUPABASE_SERVICE_ROLE_KEY`, `PUSH_VAPID_PRIVATE_KEY`, `PUSH_VAPID_SUBJECT`, а для проверки фото — `OPENAI_API_KEY`.
- Для защищённого cron route предусмотрен `CRON_SECRET`. Поскольку Vercel/сервер пользователя может не поддерживать cron, часть фоновых действий вызывается при активности приложения через `/api/routine/reminders`, `/api/tasks/recurrences` и `/api/push/sync`.
- Storage buckets создаются миграциями, среди них buckets для отчётов смен, чек-листов, закупочных файлов и фото распорядка. Ошибка `Bucket not found` означает, что соответствующая миграция Storage не применена к целевому проекту.
- Все exposed public tables/functions должны иметь подходящие grants и RLS. RLS-политики являются частью миграций, но актуальность cloud-схемы нужно проверять применением всех миграций и тестовым запросом.

## Принятые решения и ограничения

- История смен, зарплаты, сотрудники и магазины не уничтожаются физически без крайней необходимости; используется архивирование/мягкое удаление.
- Финансовые расчёты выполняются PostgreSQL/RPC, а не в браузере.
- Google Sheets и внешние интеграции не являются источником истины после сохранения фактов в PostgreSQL.
- Уведомления в приложении и push — разные каналы; успешное создание первого не гарантирует второе.
- Мобильная навигация должна быть фиксированной через portal/fixed positioning, учитывать safe area и не исчезать при скролле.
- Для широкого графика допустима горизонтальная прокрутка; на мобильном нужен landscape-friendly просмотр.
- PowerShell в рабочем окружении не принимает `&&`; команды запускаются отдельно или с `;`.
- Секреты никогда не коммитятся в репозиторий и не передаются во frontend.

## Дополнение: менеджерская главная

Для обычного менеджера главная страница имеет компактную композицию: имя учётной записи, кнопка выхода и уведомления в шапке; блок текущей смены с открытием, названием магазина, датой, наличными, закрытием и пересчётом; блок распорядка с зонами «Утро» и «Вечер»; ближайшие задачи и график. Пункты «Смены» и «Распорядок» скрыты в его нижней навигации, но доступны из соответствующих ссылок.

Открытие смены защищено проверкой активного участия сотрудника и базовым триггером с advisory-lock по сотруднику для активной смены основного продавца. Это предотвращает новые дубли даже при параллельных запросах и не требует удалять старые исторические дубли. Для менеджера основной продавец принудительно равен текущей учётной записи.

Независимый пересчёт текущей кассы хранится в `store_cash_counts`. В форме пересчёта используются купюры от 50 рублей и выше, отдельное поле «Мелочь», построчные суммы и общий итог. Последний пересчёт магазина используется для суммы на главной менеджера. Закрытие смены из этой компактной карточки открывает обычную форму закрытия без покупюрника, но с остальными полями и фото отчёта.

Обычный менеджер может открыть архив проведённых чек-листов только для магазина своей текущей открытой смены. При среднем балле ниже 10 после сохранения и фотографий создаётся одна задача с `source_checklist_submission_id`, названием «Исправить недочёты проведённого чек листа» и заданным описанием.

Дополнительные ключевые файлы: `src/components/cash-recount-form.tsx` и `src/app/shifts/recount/*` реализуют пересчёт текущей кассы; миграция `supabase/migrations/20260908120000_manager_home_shift_cash_and_checklist_tasks.sql` добавляет `store_cash_counts`, связь задач с чек-листом, RLS и защиту активных смен.

Для управляющего главная показывает только смены графика на следующий календарный день. Карточки распорядка исключают магазин склада. Страница конкретного утреннего/вечернего распорядка разрешает роли управляющего, супер-администратора и разработчика выбрать доступную смену подконтрольного магазина независимо от её статуса; обычный менеджер по-прежнему работает только с собственной открытой сменой. На корневом экране задач управляющего есть отдельная ссылка-карточка на задачи, назначенные ему лично.
Дата «завтра» для главного графика управляющего рассчитывается в часовом поясе `Asia/Vladivostok`. Сохранение текста распорядка сначала использует авторизованную SQL-функцию, а при её ошибке после серверной проверки роли и доступного магазина повторяет запись через service-role с пересозданием пунктов и ключей.
